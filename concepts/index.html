01 / Model behaviour

State machine

A set of states and rules for moving between them. It tells you what an event means given the state you are in.

Used in: countdown timer

Idle / Running / Paused / Finished. Pause saves a duration; Resume creates a new running deadline. A duplicate Start must not create parallel timers.

Why not a handful of booleans?

Separate flags such as isRunning, isPaused and isFinished can describe contradictory combinations. An explicit state lets you reject illegal events and test a small transition table. This is a modelling choice, not a requirement to use a particular library.

02 / Measure time

Android clocks

Elapsed means “time that has passed.” Monotonic means the clock does not jump backwards. Neither word means the value survives reboot.

ClockAnswersTrap
currentTimeMillis()Wall date/time since the Unix epoch.Can jump with clock correction or manual changes.
uptimeMillis()Time since boot, excluding deep sleep.Sleep would not count toward your duration.
elapsedRealtime()Time since boot, including deep sleep.Resets on reboot.
Used in: countdown timer

Measure the running interval with elapsed time. Reboot recovery uses an explicitly less trustworthy wall-time fallback. A timezone display change alone does not alter an epoch-millisecond deadline.

How does the OS know time if my app is not counting?

Your app reads operating-system clocks rather than generating time by running a loop. The OS uses clock and timing facilities below your process. The useful Android contract is the table above: choose the clock by its behaviour, not by whether your coroutine happens to be executing. The underlying implementation is device/platform-specific.

Source: SystemClock API. The reboot strategy is our design choice, not a built-in guarantee.

03 / Schedule work within a process

Coroutine delay

delay() suspends a coroutine without holding a thread. On normal completion, at least the requested time has passed; cancellation can prevent its continuation from running.

Used in: countdown timer

Pace visible redraws. late or missing redraws must not change the derived remaining time. Delay is not the completion scheduler after process death.

What is happening internally?

At a useful high level, the coroutine's continuation is retained and a future resumption is arranged. It can resume only when its dispatcher can execute it. The exact timing mechanism is dispatcher-specific; a Main dispatcher and a general worker dispatcher need not implement it identically.

The coroutine is not secretly running in another process. If its app process dies, its in-memory continuation is gone.

Source: Kotlin delay API. For process lifetime, see the app-lifetime entry.

04 / Arrange a future event

AlarmManager

An Android system service for time-based event delivery outside your app's lifetime. It is a scheduler, not persistent storage for your entire timer model.

Used in: countdown timer

Arrange completion at the run's deadline. elapsed-time alarm types match our running clock; wakeup and idle-delivery behaviour are separate choices.

Where does the alarm live when my process dies?

Android's system alarm infrastructure owns the registration. “Outside your app process” does not mean “without any process.” A PendingIntent-based registration can outlive ordinary app process death; a callback tied to a live app object is not interchangeable.

Exact versus inexact, and what can still go wrong?

setExact() alone is not idle-mode delivery. setExactAndAllowWhileIdle() supports idle delivery, but capability checks and rate restrictions apply. Choose only for a justified user-facing need. Force-stop, power-off and lost registrations after reboot still bound the promise.

On applicable API/target combinations, check canScheduleExactAlarms(). Do not assume SCHEDULE_EXACT_ALARM is pre-granted. USE_EXACT_ALARM has restricted eligibility and policy requirements; it is not a general permission shortcut.

Sources: AlarmManager API, scheduling and exact-alarm access, Doze restrictions.

05 / Delegate an action

PendingIntent

A system-held token describing an action another process can perform later on your app's behalf. It is neither the timer nor the code that handles completion.

Used in: countdown timer

Connect the alarm to an explicit receiver. identify the specific run so a late event cannot finish a newer timer.

How do I avoid replacing or cancelling the wrong alarm?

PendingIntent matching depends on operation type, request code and matching Intent fields; extras alone do not make a new identity. One approach is an explicit receiver and a URI containing timer ID and revision. Save enough information to recreate that identity for cancellation.

Prefer immutable tokens when mutation is unnecessary. The receiver must still validate the saved run; a unique token is not a substitute for checking current state.

Source: PendingIntent API. URI/run-version design is a proposed approach.

06 / Enter an app to handle an event

BroadcastReceiver

An Android component that handles a delivered broadcast. A manifest entry describes an eligible entry point; it is not an object waiting forever in memory.

Used in: countdown timer

Handle completion and restore after boot. completion validates a run; boot reconstructs scheduling from durable state.

What work is safe inside a receiver?

Keep it short. If finishing bounded asynchronous I/O with goAsync(), complete its pending result within the receiver's time budget. Do not start an unowned coroutine, return from onReceive() and assume the process must stay alive. Long work needs an appropriate background mechanism.

What about alarms before the first unlock after reboot?

Credential-protected storage is unavailable before the first unlock. Supporting that period needs Direct Boot-aware components, device-protected storage for the necessary state and the appropriate boot event. The worked problem defaults to recovery after normal boot/unlock; before-unlock alerts are an additional requirement.

Sources: Broadcasts overview, Direct Boot.

07 / Keep accepted state

Durable state and reconciliation

Durable state outlives application memory. Reconciliation means reading that accepted state and repairing its external representation, such as a missing alarm.

Used in: countdown timer

Persist transitions and deadlines; reconcile scheduling. writing a record and registering an OS alarm are not one atomic commit.

DataStore, Room, ViewModel or saved UI state?

A ViewModel holds UI-related state in memory; it is not the durable store. A small, coherent DataStore snapshot can fit one timer. Room is useful when queries, multiple records or transactions are needed. Saved UI state can help reconstruct a screen but is not the authority for background delivery.

Choose the minimum storage contract that preserves a complete transition. Do not add a database just to save a ticking number.

How can I identify a boot?

On API 24+, Settings.Global.BOOT_COUNT is a possible boot identifier to persist with the record. Handle inability to read a valid value. If boot identity is unknown, apply the chosen fallback policy rather than trusting a numeric comparison between elapsed timestamps.

Sources: DataStore, Room, ViewModel, BOOT_COUNT. Reconciliation is the proposed design, not an automatic guarantee from these APIs.

08 / Match execution to the need

Foreground service and WorkManager

A foreground service supports eligible ongoing, user-noticeable work. WorkManager schedules durable work whose execution may be deferred. Neither is the duration clock.

Considered in: countdown timer

Choose the right background tool. neither is needed merely to wait for zero. Optional audio playback after completion would introduce a different execution requirement.

Why not keep a foreground service alive for every timer?

A service does not make callback counting accurate. It adds user-visible and platform obligations. Background-start restrictions, declared service types and type-specific permissions can apply. Use one only for justified work with an eligible type, not as a generic survival mechanism.

Why is WorkManager not an exact timer?

Its execution depends on scheduling and constraints, not just the requested time. Periodic work has a minimum repeat interval of 15 minutes; one-time work also does not promise exact delivery at its initial delay. It may fit later analytics or cleanup, not this timer's precision contract.

Sources: Foreground-service restrictions by platform/target level, WorkManager requests and timing.

09 / Present state outside the screen

Notification chronometer and permissions

A notification is system-managed presentation. A chronometer can update a time display without per-second posts from your app. It does not replace expiry handling.

Used in: countdown timer

Show the remaining time outside the Activity. Pause freezes the display; finish replaces it. The durable run remains authoritative.

What is the countdown setup? 
// Platform API sketch: countdown support requires API 24+.
// Channel creation and notification permission are separate.
builder
    .setWhen(System.currentTimeMillis() + remainingMs)
    .setUsesChronometer(true)
    .setChronometerCountDown(true)

Here setWhen uses wall time, not an elapsed timestamp. Rebuild the display from current state after recovery or relevant time/state changes. OS presentation is not your completion event.

Does a foreground service need notification permission?

On Android 13+, launching a foreground service does not itself require POST_NOTIFICATIONS, but the service must still provide its notification. With permission denied, its notice appears in Task Manager rather than the notification drawer. Ordinary completion notifications generally do need permission. Starting the service has separate eligibility and permission checks.

Sources: Notification.Builder chronometer, Notification runtime permission.

10 / Name the interruption precisely

Activity, process and package lifetime

A screen, an app process and an installed package have different lifetimes. “The app was killed” is not enough information to choose recovery behaviour.

EventWhat not to assume
Screen leaves / Activity recreatedThe timer should not restart with the screen.
Process reclaimed for memoryNo in-process coroutine or ViewModel survives.
Task swiped awayIt is not the platform's Force Stop action; device behaviour can vary.
Force StopNo self-restart guarantee; package stopped state must be respected.
RebootDo not reuse old elapsed timestamps or assume alarm registrations remain.
Used in: countdown timer

Choose the recovery path. ordinary process death can preserve an OS-held scheduled action; force-stop is an intentional boundary, not a reliability bug to bypass.

Sources: Process lifecycle, Android 15 stopped state. On Android 15, entering stopped state also cancels pending intents.

11 / Separate elapsed time from execution

Deep sleep, Doze and powered off

Deep sleep is a low-power condition in which application code may not execute. Doze is an Android policy restricting background work during device inactivity. Powered off means the normal Android OS is not running.

Used in: countdown timer

Count sleeping time with the right clock; choose idle-aware delivery if justified. a clock progressing is not proof an app callback is executing.

Does exact mean unaffected by Doze?

Not by itself. Standard alarms can be deferred in Doze, including setExact(). Idle-aware APIs have a different contract and frequency restrictions. They are for selected events, not a way to run a one-second background ticker.

Can an ordinary app power on the phone for an alarm?

Do not assume it can. A device manufacturer's powered-off alarm feature is not the generic AlarmManager contract. For this problem, explain what recovery should show after boot instead of promising execution while the OS is off.

Sources: Doze and App Standby, SystemClock, Alarm scheduling and reboot.
