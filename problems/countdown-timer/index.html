Timers / Worked example

Countdown timer

Design an Android timer with start, pause, resume and reset. Then handle completion in the background and restore the timer after process death or reboot.

The main decision is how to represent time. Store a deadline, not a number that must be decremented every second. Background alerts and recovery need separate handling.

Read the designRevision notesRelated questions

Assumes working knowledge of Kotlin and Android. Code is illustrative; this is a design walkthrough, not a tested Android app. Platform references checked 28 October 2026.

01 / Requirements

Clarify what happens when the app is closed

Practice prompt

Design an Android countdown timer. Let the user start, pause, resume and reset it. Show the remaining time, and explain what happens when the screen disappears, the process dies or the device restarts.

This is a synthesised learning prompt, not a verbatim Google question. Compose, reboot recovery and the policies below are explicit practice choices, not requirements shared by every interview report. Prompt provenance.

Separate the correct remaining time from a timely completion alert. You can restore the first without having delivered the second.

The distinction between process death and force-stop is a platform boundary, not a clever implementation challenge. Read the lifetime comparison.

Check: what are the three independent jobs?

Answer
Measure remaining time. Deliver completion. Recover the accepted timer state. Do not select one Android API and assume it solves all three.

02 / State transitions

Idle, Running, Paused and Finished

A timer needs four states: Idle, Running, Paused and Finished. A button is an event that changes a state, not permission to start another independent ticking job.

Store the original duration for Reset. While Paused, store a remaining duration. While Running, store enough information to calculate that duration; the next stage decides what that is.

Do not add yet

No service, alarm or boot receiver is needed just to explain these states. Those enter only when a requirement needs them.

Wiki: state machine

Check: what happens if Start is tapped twice?

Only one Running state exists. Handle commands through one state owner. Starting a new coroutine for every tap would make concurrency an accidental part of the design.

03 / Timekeeping

Calculate remaining time from a deadline

The tempting approach is delay(1000); remaining--. Now imagine the callback is not run for five seconds: subtracting one would make the timer four seconds late.

Count callbacks

“One callback ran, so one second passed.”
Missed or late callbacks change the answer.

Calculate from a deadline

“The deadline is fixed. What time is it now?”
A late redraw still gives the correct answer.

For this duration timer, use elapsedRealtime() within one boot. It includes deep sleep and is not changed by a user adjusting the date. [1]

// Illustrative Kotlin: one boot, a running timer.
val endElapsedMs = nowElapsedMs + durationMs

fun remainingMs(endElapsedMs: Long, nowElapsedMs: Long): Long =
    (endElapsedMs - nowElapsedMs).coerceAtLeast(0L)

For a five-minute timer: start at elapsed time 100 seconds, so the deadline is 400 seconds. If the next redraw happens at 107 seconds, show 293 seconds remaining, regardless of how many callbacks ran.

Pause: save remainingMs(deadline, now). Resume: make a new deadline now + pausedRemaining. Keep Reset's original duration separate.

Does delay(1000) not mean one second?

It suspends for at least the requested duration on normal completion; it does not reserve CPU execution at exactly the one-second mark. Cancellation may prevent the code after it from running. Use it to pace a visible redraw, not to count elapsed seconds. How the coroutine resumes. [2]

What do elapsed, monotonic, uptime and wall time mean?

Elapsed means time that has passed. A monotonic clock does not jump backwards when the user changes the date. Android exposes clocks with different sleep and reboot behaviour. Compare the three clocks, with one example.

What does it mean for the CPU to sleep?

Your app might execute no instructions for a while; time still passes. Deep sleep and Android's Doze policy are related to power saving but are not the same thing. See deep sleep versus Doze.

Check: the UI misses eight ticks. What must you repair?

Nothing in the time model. Read the clock and recalculate. The UI ticker is disposable; the deadline is not.

04 / High-level design (HLD)

Components and data flow

The Activity and the completion receiver are two entry points into the same timer. Neither owns a separate countdown. A coordinator applies commands to the durable record; the UI derives its display from that record and the clock.

Example: start a five-minute timer and leave the app

  1. The coordinator reads elapsed time and saves Running with a five-minute deadline and a new run revision.
  2. The scheduler registers a completion event for that run. The UI redraws while visible; leaving the screen stops those redraws, not the timer.
  3. When Android delivers the event, the receiver asks the coordinator to finish that run. It checks the stored revision and deadline before updating state and posting a notification.
  4. On reopening the app, the screen reads the record and recalculates the display. It does not restart the original five minutes.

Why separate these components? Time calculation can be tested without Android. The receiver can use the same rules without an Activity or ViewModel. The storage and alarm calls remain separate operations; their failure gap is covered in the low-level design.

This component split is one design choice. Android recommends separation between UI and data layers; an additional domain coordinator is useful here because the UI and receivers share transition rules. Architecture reference [6].

05 / Background completion

Schedule a completion event

The deadline answers “has it expired?” It cannot execute your code. Give the completion event to AlarmManager, rather than keeping a coroutine alive just to wait.

Three roles, not competing tools: AlarmManager chooses when; a PendingIntent is the delegated action; a BroadcastReceiver contains the handler. An ordinary registered receiver does not schedule itself.

Delivery limitations

Precise, user-facing completion may justify a one-shot exact alarm. For idle delivery, consider the appropriate allow-while-idle API; check exact-alarm capability. If access is unavailable, explain the limitation and request it where appropriate, or offer an explicitly best-effort mode. Neither mode guarantees an alert at the exact millisecond. [3] [4]

A correct timer can still have an invisible alert when notifications are denied. Exact-alarm access and notification permission are separate checks. Neither means the phone can alert while fully powered off.

If the receiver can wake my app, why do I need a PendingIntent?

The receiver tells Android where your handler is, not when to invoke it. The PendingIntent gives the scheduler a system-held reference to an action it may perform later on your behalf. Identity, lifetime and safe construction.

How can an alarm survive if the app's process is gone?

The scheduling is outside your process, not outside all processes. Android's system service retains the alarm registration; an eligible broadcast can create your app's process to run its manifest receiver. Device reboot and force-stop are different cases. Read the system-service explanation.

Can I guarantee the alarm at the exact millisecond?

No end-to-end hard real-time promise. Permissions, device availability and platform restrictions still matter, and executing the receiver and presenting an alert take time. AlarmManager is a scheduling capability, not proof the user heard something. See exact-alarm boundaries.

How does a notification keep showing the countdown?

A platform notification chronometer can update its displayed count without your app posting every second. It is a display, not your completion scheduler. Reconcile it on pause, reset, recovery and finish. Countdown setup and permission nuance.

Coroutine, alarm, foreground service or WorkManager?

For this design, a waiting countdown alone does not justify a permanently running service. Sustained alarm audio is a separate requirement that may need an eligible service and a fresh review of its restrictions. Wiki: foreground services and WorkManager.

Check: why not one WorkManager task per second?

That is not its scheduling contract. We need one completion event and cheap UI redraws while visible, not persistent second-by-second background execution.

06 / Recovery

Process death, reboot and force-stop

Lifetime details; reboot scheduling [3]; stopped-state behaviour [5].

Why save two deadlines?

Save an elapsed deadline for the current boot and a wall-time deadline for fallback. Also identify the boot; comparing elapsed numbers alone cannot reliably detect a reboot. Record and boot-identity choices.

12:00Start five minutes.
Save wall deadline 12:05.
12:02Device restarts.
Elapsed clock resets.
12:03Recovery runs.
12:05 - 12:03 = two minutes.

This example assumes the wall clock stayed trustworthy. During the same boot, manual date changes do not affect our elapsed deadline. Across reboot, a wall-clock jump can change the recovered answer. Saving two deadlines does not resolve an untrusted wall clock.

Explicit product policy

Our practice policy counts powered-off time using the saved wall deadline. If that clock cannot be trusted, we cannot prove the true elapsed duration across reboot. A different product might pause on reboot or use a trusted external time source; that is a different promise, not a missing API call.

How does a boot receiver run if my app was already closed?

A manifest-declared receiver is an entry point Android may instantiate; it does not require the old Activity to be alive. Declare RECEIVE_BOOT_COMPLETED, persist state beforehand and reschedule eligible alarms after boot. This assumes the app has been launched and is not blocked by stopped state. Before-first-unlock delivery additionally needs Direct Boot-aware components and suitable storage; it is outside this lesson's default scope. Receiver and Direct Boot details.

I have heard alarms can ring when the phone is switched off. How?

Some devices may provide manufacturer-specific powered-off alarm features. A normal app cannot assume those. Our Android scheduling design requires a running OS; after boot, it can recover and apply a missed-alert policy. Sleep, Doze and powered off are different.

Missed-alert choice: if recovery finds an overdue run, show a “timer ended while unavailable” result. Do not silently replay a loud alarm hours later. That is our practice policy, to clarify with the interviewer.

Check: an app process dies, but the device never rebooted. Which clock wins?

The persisted elapsed deadline, provided the boot identity matches. Losing application memory does not reset Android's elapsed clock.

07 / Low-level design (LLD)

Data model, interfaces and command handling

The screen sends actions; the receiver delivers completion. Both use the same timer rules and durable record. The notification and Compose UI are two views of that state, not two independent timers.

PieceIts responsibility in this design
Compose + ViewModelRender lifecycle-aware UI state; send actions; redraw while visible.
Timer coordinator / domain rulesSerialize commands, transition states and reject stale run versions.
Repository + durable storeKeep the accepted run, deadlines and delivery state after process death.
Clock + scheduler adaptersRead the selected clocks; register/cancel the desired alarm.
Completion / boot receiversValidate or restore state; do bounded work; request the appropriate notification.

The boundaries above are a proposed design. UI/data separation is recommended; an extra domain layer is a choice, not a rule that every small Android app must follow. [6]

Interfaces

The following contracts describe responsibilities, not complete Kotlin implementations. update must atomically read and replace a record; it must not make OS calls inside the storage transaction.

interface TimerClock {
  fun elapsedMs(): Long
  fun wallMs(): Long
  fun bootId(): Long? // null when a valid identity is unavailable
}

interface TimerStore {
  fun observe(): Flow<TimerRecord>
  suspend fun update(
    transition: (TimerRecord) -> TimerRecord
  ): TimerRecord
}

interface CompletionScheduler {
  fun schedule(run: RunKey, deadlineElapsedMs: Long): ScheduleResult
  fun cancel(run: RunKey)
}

data class RunKey(val timerId: String, val revision: Long)

ScheduleResult distinguishes registered, permission-required and failed attempts. It is not a delivery receipt. A coordinator serializes commands and their scheduling effects within the application process. If separate processes are introduced, this in-memory serialization is no longer sufficient.

Stored record 
TimerRecord(
  timerId,
  revision,
  status,              // Idle / Running / Paused / Finished
  originalDurationMs,
  pausedRemainingMs,
  endElapsedMs,
  endWallMs,
  bootCount,
  desiredAlarmRun,      // RunKey or absent
  registrationStatus,  // Unknown / Registered / Unavailable
  completionDelivery   // None / Pending / Posted
)

This is a schema sketch, not production-ready Kotlin. Fields are state-dependent. Store one coherent record, not independently updated preference keys. A small snapshot store may suffice; use database transactions when multiple rows or timers need atomic changes. Storage trade-offs.

originalDurationMs belongs to the configured timer. Deadlines and alarm identity belong to a Running revision; a Paused record keeps only its frozen remaining duration. Treat incompatible field combinations as invalid rather than allowing every nullable-field combination.

Command transitions
  1. Start / Resume: sample both clocks, advance the run revision, commit Running with deadlines, then register that run's completion.
  2. Pause: compute the remaining duration; if already zero, settle Finished instead. Otherwise commit Paused with a new revision, then cancel the old alarm.
  3. Reset: commit Idle with the original duration and a new revision; cancel obsolete delivery and update the notification.
  4. Finish: re-read the record; require the matching run, Running state and a reached deadline. Settle Finished once, then perform the notification step.

Concurrency assumption: one application process. Serialize screen and receiver commands through a shared coordinator and transactional state update; do not rely on a ViewModel-only mutex. A receiver must finish bounded work correctly rather than launch an unowned coroutine and return. Receiver lifetime.

Completion algorithm

// Pseudocode: run through the shared serialized coordinator.
onCompletion(eventRun):
  record = store.read()
  if record.runKey != eventRun: return
  if record.status != Running: return

  remaining = recoverRemaining(record, clock)
  if remaining > 0:
    reconcileSchedule(record)
    return

  store.commit(Finished, completionDelivery = Pending)
  notifications.post(stableNotificationId, finishedState)
  store.markPostedIfStillCurrent(eventRun)

The store methods above abbreviate atomic state operations. Re-read and validate inside the update; do not rely on an earlier unlocked read. A wall-time recovery can require a new elapsed deadline before scheduling. Notification errors leave delivery Pending for the declared recovery policy.

Reject completion from an old run

Imagine Pause commits just as an old completion event arrives. Checking the durable revision and state makes that event harmless. Use the timer/run identity in the PendingIntent's matching identity, not only in extras. Why extras alone do not identify an alarm.

Harder follow-up: what if the process dies between saving and scheduling?

A storage commit and an OS alarm registration are not one transaction. Persist the desired schedule, attempt registration and reconcile it on available entry points such as reopen, boot and capability changes. A “scheduled” flag alone is not proof the OS still holds it.

Residual gap: if the process dies before registration and no eligible entry point runs, immediate completion delivery is not assured. State recovery can still be correct. State this limit rather than claiming the two operations are atomic.

Harder follow-up: can completion notification be exactly once?

Committing Finished and posting a notification are also separate effects. Keep completion delivery pending until handled, and use a stable notification ID to avoid multiple visible entries. A retry may still replay an alert; visible-entry deduplication is not proof of exactly-once sound. Choose the recovery behaviour explicitly.

Check: do you need to save the remaining number every second?

No. Save durable transitions and deadlines. Derive a visible remaining number from the clock. Per-second writes add work without improving this model's timekeeping.

Revision

Design summary

Use an elapsed-time deadline for a Running timer and a frozen duration for a Paused one. Save transitions rather than per-second ticks. Register completion with Android, validate the run when it arrives, and restore state using a documented reboot policy. Alarm registration and storage are not one transaction.
